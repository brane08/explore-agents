Companion to `design/repo-brief.md`. Snapshot of what's built, what's designed
but unbuilt, and what's still open, as of branch `design/shadow-divergence` (`e941224`).

## Done and merged to `main`

- **Phase 0 — deterministic foundation.** `lockbuild` stages, `tags.yaml`, CI gates.
- **Phase 1 — routing + B1.** Router cascade, B1 runtime tool assembly, the FastAPI
  console.
- **Phase 2 — B2b + human-gated certify.** One real capability,
  `cron-next-fire-times`, went generation → `_proposed/` → certify → PR → merge →
  `quarantined` trust record, closing the phase's exit criteria (PR #3).
- Two review notes opened during Phase 2 closed after merge, both on `main` (PR #4 plus a
  direct fix):
  - A determinism defect in `lockbuild` hashing — `__pycache__` produced by certify's own
    eval run was entering the entry content hash, so a lock built after an eval run
    wouldn't match a clean checkout of the same commit. Found via `lockbuild verify`
    failing on a merge-ready branch; fixed test-first
    (`tooling/lockbuild/tests/test_trust_semantics.py::test_build_artifacts_do_not_enter_the_hash`).
  - A truncated `routing_summary` in `cron-next-fire-times/entry.yaml` — the certify-model
    summary-writer stub was reading spec.md's first physical line instead of the first
    sentence, publishing a mid-sentence fragment into router context. Fixed and the live
    catalog entry regenerated by running the fixed writer, not hand-edited.

## Designed, not yet built (Phase 3 prerequisite)

- `design/2026-08-13-shadow-divergence-design.md` — approved design for supervised
  invocation, the mechanism that lets a `quarantined` entry earn `validated`. Two modes,
  one evidence ledger: **shadow** (mechanical field-wise diff against the entry the router
  would otherwise have picked, structured output only) and **canary** (a human adjudicates
  a real invocation, for prose output or when no counterpart exists). Clean-streak
  promotion — N consecutive clean runs, any incident resets to zero, voided runs count for
  neither. Runs live in the orchestrator's SQLite store; only the promotion decision
  reaches `trust.yaml`, written by `certify` with a content-addressed evidence digest.
- `design/plans/2026-08-13-supervised-invocation-plan.md` — the implementation plan for
  that design. Seven TDD tasks, dependency-ordered: supervised-run ledger → mode selection
  → field-predicate divergence comparison → wiring into the invoke path → canary review
  screen → certify-side promotion → recall regression. Not executed — per the
  one-phase-per-session rule this needs the user to name "Phase 3" in a session to start.
- A known gap the plan closes: `allowed_tiers` today grants operators every tier,
  including `quarantined` — an operator invoking a quarantined agent currently gets an
  **unsupervised** run, which is a live violation of `CHECKLISTS.md` layer 8's `[M]` item
  "quarantined agents run only in supervised mode." Task 4 of the plan fixes this.

## Logged, deferred, not designed

- `design/2026-08-13-mcp-discovery-indexing-future-phase.md` — an external "MCP
  Discovery & Indexing" work package, assessed against this repo and filed as a
  future-phase note rather than adopted now. `CATALOG.md` §6 already names this exact
  evolution (embedding index fronting the router) as a deferred scaling trigger past
  ~500 catalog entries — the catalog currently holds 4 (2 skills, 1 mcp-tool, 1 agent, 1
  model), nowhere near that gate. Two of the brief's decisions (no LLM in the router hot
  path; MCP registry as a projected view of enterprise catalogs) reverse rather than
  extend standing `docs/CATALOG.md` policy and would need an explicit human spec edit
  before implementation, not just a design doc. Also logged there: a router
  token/candidate cap is needed regardless of which retrieval approach eventually lands —
  today's router scores every `skill`/`mcp-tool` entry with one uncapped model call per
  candidate, with no shortlist or per-request budget.
