# CATALOG.md — Capability Catalog Specification (v3.1-beta)

> **Status: BETA (draft).** These specifications are under active iteration during the
> POC phases and are expected to change. Nothing here is a frozen contract yet: breaking
> revisions are permitted between phases, spec changes remain human-only (separate PRs),
> and consumers must pin the document version/hash they were built against.

Defines the co-located capability catalog for the orchestrator: protocol layer, repo
layout, entry schemas, lockbuild, trust model, certification/promotion, template
graduation, and model-agnosticism rules. The router loads **only** `catalog.lock.yaml`.

---

## 1. Routing cascade (system contract)

```
task → match existing agent → post-match confirmation → invoke
     → match template                 → B1.5 instantiate (fill slots, validate)
     → tool/skill coverage, no shape  → B1 runtime assembly (result registered, §5)
     → residual gap identified        → B2 (delta preferred) via playbook → _proposed/ → certify
     → nothing recognized             → ERROR: PATTERN_UNRECOGNIZED (structured, logged)
```

- **Post-match confirmation:** after an agent match, a cheap model call scores whether the
  agent's full `detail` actually covers the task; below threshold → treated as no-match
  and the cascade continues. Silent misroute of certified capability is costlier than an
  extra call.
- Hard-stop policy: no fuzzy fallback between tiers. Escalation on any error is an
  explicit orchestrator decision with the structured error as input — never automatic.
- Error records (`PATTERN_UNRECOGNIZED`, `SLOT_*`) are persisted after a hygiene pass
  (strip raw user text to normalized capability statements) — this corpus is the B2
  backlog and template-gap signal (§9).

## 2. Protocol layer

Two planes, two standards — both vendor-neutral by construction:

**Capability plane — MCP.** All tool access is MCP (or local skills exposing the same
tool-schema shape). Tool schemas are the contract boundary; mirrored snapshots are the
hash source (§4). No bespoke tool integrations outside MCP.

**Delegation plane — A2A.** All agent-to-agent interaction — internal or external — is
expressed in A2A semantics and is **router-mediated**:
- Agents never bind or invoke other agents directly (playbook §3.1/§8). They declare
  `delegation_requirements`; at runtime the orchestrator resolves these through the
  router, so every delegation re-passes trust checks and post-match confirmation.
- **External agents** enter the catalog as `kind: a2a-agent`: their Agent Card is
  mirrored (`agentcard.snapshot.json`) exactly like an MCP schema — fetched at lockbuild
  `--refresh`, normalized, hashed, routing summary regenerated by our model from the
  card's declared skills, never from vendor prose. They start `untrusted` and pass the
  same tool-style certification before `validated`.
- **Exposure (optional):** promoted internal agents may be published behind an A2A server
  endpoint; the generated Agent Card is derived from the lock entry (id, version,
  routing_summary, declared skills), so external description can never diverge from
  certified reality.

Rationale: MCP standardizes what an agent *uses*; A2A standardizes what an agent *is* to
other agents. Keeping delegation off the binding surface and on the routed A2A plane
resolves transitive-trust and cycle risks structurally.

## 3. Repository layout

```
agent-platform/
├── catalog.lock.yaml           # GENERATED. Router input. Never hand-edited.
├── trust.yaml                  # (id, version, model_profile) → tier + provenance
├── tags.yaml                   # controlled capability_tags vocabulary (lockbuild-validated)
├── models/<id>/entry.yaml      # model profiles (§4)
├── skills/<id>/{entry.yaml, SKILL.md, impl/}
├── mcp/<id>/{entry.yaml, schema.snapshot.json, routing_summary.md}
├── a2a/<id>/{entry.yaml, agentcard.snapshot.json, routing_summary.md}
├── templates/<id>/{entry.yaml, impl/, prompts/, ui/, evalmatrix/}
├── agents/
│   ├── <id>/{entry.yaml, AGENT_MANIFEST.yaml, src/, prompts/, tests/, eval/}
│   └── _proposed/              # B2 candidates. EXCLUDED from lock. Certify-only exit.
└── tooling/{lockbuild/, certify/}
```

Co-location invariant: a git SHA is a complete consistency snapshot; the orchestrator pins
a SHA per routing epoch.

## 4. Entry kinds

Common fields: `id` (globally unique), `kind`, `version` (semver), `routing_summary`
(1–2 sentences — regenerated from schema/card for external kinds; this is a security
control, not hygiene: tool-description poisoning is a documented attack class in
enterprise/finance deployments — malicious instructions embedded in vendor MCP tool
descriptions execute with the agent's own credentials through an approved channel.
Vendor prose therefore never reaches router or agent context; only our regenerated
summary and the raw schema do), `capability_tags`
(validated at lockbuild against `tags.yaml` controlled vocabulary), `detail` (lazy-loaded).
Trust tier is never in `entry.yaml` — authors don't self-declare trust.

| kind | extra fields | hash scope |
|---|---|---|
| `skill` | — | `SKILL.md` + `impl/**` |
| `mcp-tool` | `registry_url` | `schema.snapshot.json` |
| `a2a-agent` | `endpoint_url` | `agentcard.snapshot.json` |
| `model` | `provider`, `endpoint_class` (`anthropic`\|`openai-compat`\|`bedrock`\|`local`), `capabilities` (`tool_use`, `structured_output`, `context_window`, `parallel_tools`), `cost_class`, `profile_class`, `status: active\|deprecated` | `entry.yaml` |
| `agent` / `component` | `bindings: [{id, version}]`; component: `conforms_to: {template_id, slot}`; `model_requirements` (capability predicates, not model ids); `delegation_requirements` | `AGENT_MANIFEST.yaml` + `src/**` + `prompts/**` + `tests/**` + `eval/**` |
| `template` | `slots` (below), `fixed: impl/`, `model_requirements` | `entry.yaml` + `impl/**` + `prompts/**` + `ui/**` + `evalmatrix/**` |
| `composite` | `members: [{id, version}]` | `entry.yaml` (members transitive) |

**Template slots:**
```yaml
slots:
  - name: <slot>
    type: binding | value | enum
    required: true|false
    accepts: {capability_tags: […], max_tier_required: <tier>}   # binding
    schema: {format: <fmt>, validated_by: impl/<validator>}       # value
    accepts: [<variant>, …]                                       # enum ("defined loops")
```
**Slot expressiveness ceiling (hard rule):** `value` slots carry only deterministically
validatable data. Anything Turing-complete is a template version bump or a B2 task.

**Binding restriction (hard rule):** `bindings` may reference only `skill` and `mcp-tool`
kinds. Agent/component/a2a-agent references in bindings → lockbuild failure. Delegation
is expressed via `delegation_requirements` and resolved by the router (§2).

**Model resolution:** entries declare `model_requirements` as capability predicates
(`{tool_use: true, min_context: 128k}`), never concrete model ids. The orchestrator's
resolver maps requirements → concrete `model` profile at invocation (policy: cost,
availability, task class). Per-profile prompt variants live in `prompts/`
(`default.md`, `<profile_class>.md`), selected at resolution time.

## 5. B1 registration

B1 assemblies are config-only (validated tools + generated prompt). Identity = sha256 of
the assembly config. On first successful use, register as a lightweight `kind: agent`
entry (config as `src/`, prompt in `prompts/`) — skipping `_proposed/` since all parts are
already validated; entry tier = `min(binding tiers)` at the assembly's `model_profile`.
Identical future tasks route to the registered entry instead of re-assembling.

## 6. Lockbuild pipeline (`tooling/lockbuild`)

Deterministic: same tree → same lock anywhere.

**Stage 1 — scan & validate.** Walk all entry dirs (skip `agents/_proposed/`).
JSON-Schema-validate `entry.yaml`; unknown fields, bad kind, duplicate id, unknown
`capability_tags`, binding-restriction violations → build fails.

**Stage 2 — external refresh** (`--refresh` only; scheduled job): fetch MCP schemas and
A2A Agent Cards; normalize (sorted keys, strip volatile fields) before comparing; on
change write new snapshot + regenerate routing summary from schema/card. Refresh commits
to a PR branch, never `main`.

**Stage 3 — hashes.** Kind-scoped file sets (§4): sorted paths, path names in hash input,
LF-normalized, no mtimes.

**Stage 4 — trust join & integrity (lazy invalidation).**
- Left-join `trust.yaml` on `(id, version, model_profile)`; no record → `untrusted`.
- **Binding consistency:** for each agent/component, compare manifest
  `(id, version, schema_hash)` against freshly computed hashes.
  - Referenced entry **missing** from the tree → **build fails** (internal inconsistency).
  - Hash **drifted** (external refresh, skill/template edit) → entry marked
    `stale: true, stale_reason: <binding-drift|template-drift|model-drift>` in the lock —
    build succeeds, refresh PRs merge cleanly, the **router refuses stale entries**, and
    rebase + eval-rerun happens asynchronously.
- Instance consistency (`instantiated_from` hash) and model-profile deprecation follow the
  same stale-flag path. Composite tier = `min(member tiers)` unless explicitly recorded;
  cycle detection over composites (agent-binding cycles are impossible by the §4 rule).

**Stage 5 — emit** `catalog.lock.yaml`:
`{lock_version: 3, built_from: <sha>, built_at, entries: [{id, kind, version, hash,
trust_tier, stale?, stale_reason?, routing_summary, capability_tags, detail, bindings?,
slots?, instantiated_from?, model_requirements?, delegation_requirements?}]}`

**Triggers:** CI pre-merge rebuild-and-diff (lock must match tree); nightly `--refresh`
→ drift PR; certify runs lockbuild as its final promotion step in the same commit.

**Scale note:** the lock-as-router-context design targets ≤~500 entries; beyond that, an
embedding index over `routing_summary` fronts the router (retrieval → shortlist → router
prompt). The lock format is already the corpus for that index — designed-for evolution,
not an architecture change.

## 7. Trust model (`trust.yaml`)

```yaml
- id: psql-select
  version: 1.3.0
  model_profile: opus-class-ref        # evidence is valid for this pairing only
  tier: validated                      # validated | quarantined | untrusted
  granted_by: certify-run-2026-07-12T09:14Z
  evidence: s3://certs/<content-hash>/  # content-addressed, immutable
```
- Written only by certify (or recorded human override). Append-only history.
- **Tier is per `(id, version, model_profile)`.** Certification happens against a
  **reference profile per `profile_class`** (keep 2–3 active classes or eval cost
  compounds). Running on a different member of the same class, or migrating classes,
  requires an **eval-rerun**: execute the entry's own `eval/` on the new profile; green →
  new trust record. Model migration is a rerun, never a re-certify from scratch — this is
  the payoff of every agent shipping executable evals.
- B2 outputs enter at `quarantined` regardless of eval results; fresh `mcp-tool` /
  `a2a-agent` entries enter `untrusted`.
- **Quarantine runtime semantics (evidence generator):** quarantined agents run in
  *supervised invocation* — shadow execution alongside a validated agent handling the
  same task class (outputs diffed, never returned to the caller) or canary routing with
  human-visible results and instant fallback. Promotion `quarantined → validated`
  requires N supervised runs meeting a divergence/incident threshold, or template
  graduation (§9). Without supervised mode, quarantine is theater.
- **Recall:** demoting any entry in `trust.yaml` takes effect at **routing time** —
  the router checks tier transitively (instance → template, agent → bindings) per
  invocation, independent of lock rebuild. A template demotion instantly halts all
  instances; the subsequent lockbuild enumerates them via stale flags for remediation.

## 8. Certification & promotion (`tooling/certify`)

**Honesty clause:** v1 of this gate is a **PR-generation system with mandatory human
promotion**. Gate autonomy is earned: the LLM-judge and security steps run in parallel
with human review; after N consecutive promotions (default 20) in which human review
found zero findings the gate missed, per finding-category, that category may be delegated
to the gate — recorded in `trust.yaml`-style provenance for the gate itself.

Steps, per candidate in `_proposed/`:
1. **Layout & manifest:** playbook §6 structure; `playbook_version` supported;
   `harness` on the conformance list (§10); criteria refs match the frozen inputs
   (both `behavioral_criteria_ref` and, for full-agent scope in either mode, `interface_criteria_ref` —
   the two-phase freeze: behavioral at routing, interface post-design by a separate
   model call that saw the design but no implementation).
2. **Rebase check:** any bound entry's hash moved since `catalog_ref` → rebuild against
   current `main` + eval-rerun before proceeding.
3. **Eval:** run `eval/` on the manifest's `model_profile`; all criteria green with evidence.
4. **Nearest-template eval reuse:** run evalmatrix rows whose declared interface
   signatures mechanically match the candidate — applicability is a signature check,
   never a model judgment.
5. **Structural review:** `slot_value_surface` declared and genuinely separated from
   skeleton; flag entanglement. `delegation_requirements` consistent with code (no direct
   agent invocation paths).
6. **Security review:** binding audit vs. ceiling; no manifest-bypassing I/O; MCP usage
   consistent with schemas. **Model-diversity rule:** the judge model and the criteria
   author are pinned independently in certify config (hashed) and must differ in family
   from the implementation `model_profile` where feasible — same-family self-agreement
   is a gate weakness.
7. **Promote:** generate `entry.yaml` from `entry.draft.yaml` — `routing_summary`
   regenerated by the certify model from SPEC + manifest (draft is advisory, consistent
   with the external-summary rule), `capability_tags` validated against `tags.yaml`
   (proposed tags require human approval), `model_requirements` carried over. Move to
   `agents/<id>/`; write `(id, version, model_profile)` trust record
   at `quarantined`; move `trace/` to content-addressed object storage; run lockbuild;
   commit atomically.

## 9. Template graduation (B2 → B1.5 pipeline)

- **Signal:** certify detects the Nth (default 3) structurally similar promoted candidate
  (nearest-template neighborhood or matching `slot_value_surface` shapes).
- **Extraction:** factor shared skeleton into `templates/<id>/impl/` + `prompts/`;
  enumerate variance as slots (§4 ceiling applies); build `evalmatrix/` covering
  representative slot combinations × every enum variant, certified on the reference
  profile per supported `profile_class`.
- **Thereafter:** replication via B1.5. Instances inherit template tier capped by
  `min(binding tiers)`; instance validation = slot-check + hash-check, plus eval-rerun
  only when the instance's resolved profile differs from the template's cert profile.
- Existing lineage agents may migrate to instances (commit), shedding per-agent
  certification burden. Graduation is also the standard path for a B2 lineage to reach
  `validated` (§7): the heavy trust cost is paid once per pattern.

## 10. Harness conformance

"Follows the playbook" is harness-dependent behavior, verified once per harness/version,
not assumed. A harness enters the conformance list by passing a fixture suite: produces
the §6 layout, respects budgets, emits honest `PARTIAL` on an unsatisfiable fixture,
refuses a criteria-modification fixture, produces trace. Certify step 1 rejects
candidates from unlisted harnesses.

## 11. Error vocabulary

| Error | Meaning | Consumed by |
|---|---|---|
| `PATTERN_UNRECOGNIZED <residual>` | No agent/template/coverage match | B2 backlog; template gap analysis |
| `SLOT_UNFILLED <name>` / `SLOT_INVALID <name> <reason>` | Instantiation failures | Router-prompting eval set; template evolution |
| `DELTA_INSUFFICIENT` | Residual not component-shaped | Orchestrator escalation decision |
| `MODE_MISMATCH` / `MISSING_INPUT` | Playbook precondition failures | Invocation bug |
| `WARN: DELEGATION_REQUIRED <capability>` | Task needs another agent | Router-mediated A2A resolution |
| `WARN: CRITERIA_ISSUE` | Frozen criteria appear defective/untestable (built anyway) | Criteria-author eval set; certify review |
| `WARN: SPEC_TENSION` | Restated capability contradicts a criterion (criteria won) | Certify review |
| `STALE_ENTRY <id> <reason>` | Router refused a stale lock entry | Async rebase/eval-rerun queue |
